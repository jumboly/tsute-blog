何を書こうかと考えて、自分の仕事の経歴から書いてみようと思った。新卒で入った現場の話である。1996年のことだ。

## SQLのない現場

その現場では、OpenVMSというOSの上で開発していた。主な言語はCOBOLで、データは固定長のシーケンシャルファイルか索引編成ファイルに入っている。

RDBのように、SQLでちょっと条件を書いてデータを探す、ということはできない。「この項目がこの値のレコードだけ見たい」と思っても、気軽には取り出せなかった。

そこで現場には、SELというツールがあった。

## 元のSEL

SELは、固定長レコードのどこからどこまでが何の項目かを指定し、条件に合うレコードだけを抜き出すツールだった。実装はDCL（DIGITAL Command Language）で書かれていた。DCLはOpenVMSのコマンド言語で、今でいうシェルスクリプトに当たる。

条件は、1行に1項目ずつCSV形式で書く。開始位置、長さ、型、比較演算子、値、という並びだったと思う。比較演算子は`>`や`<`ではなく、DCLの`.GT.`や`.LE.`のような書き方だった。その行を必要なだけ並べ、最後の行に`AND`か`OR`を書いて、全部の条件をANDでつなぐかORでつなぐかを決める。

当時のものはもう残っていないので、以下は記憶をもとにした雰囲気だが、だいたいこんな感じだった。

```text
1,4,S,.EQS.,1001
21,8,I,.GE.,19960401
41,2,S,.NES.,99
AND
```

これで用は足りる。ただ、使っていると不満が二つあった。

一つは、項目を文字列か整数としてしか比べられないこと。DCLの値は、そもそも文字列か整数のどちらかしかない。[[1]](https://docs.vmssoftware.com/vsi-openvms-user-s-manual/) 比較演算子も、文字列用の`.EQS.`や`.GTS.`と、整数用の`.EQ.`や`.GT.`に分かれている。スクリプトで書いている以上、ここから先へは行きにくい。ところが、COBOLのレコードにはもっといろいろな形の数字が入っている。

もう一つは、ANDとORを組み合わせられないこと。全部ANDか、全部ORか。「Aで、かつBかCのどちらか」は書けなかった。

## Cで作り直してSEL95にした

それで、Cで作り直すことにした。名前はSEL95にした。

95年に作ったから、ではない。作ったのは1996年である。Windows 95が流行っていたので、なんとなく95を付けてみたかった。

条件の書き方は、元のSELを引き継いだ。違うのは二つ。一つは比較演算子で、`.EQ.`や`.GT.`がどうにも覚えられなかったので、`=`や`>`のような普通の記号で書けるようにした。もう一つは最後の行で、ここに行番号と括弧を使った式を書けるようにした。演算子は`&`と`|`。

```text
1,4,X,=,1001
21,8,DATE,>=,19960401
29,5,COMP-3,>,10000
1 & (2 | 3)
```

これで「1行目の条件を満たし、かつ2行目か3行目のどちらかを満たす」と書ける。こちらも雰囲気で、型の書き方などは正確ではない。

## PICTURE句の型に対応する

型は、COBOLのPICTURE句で現場で使われていたものに一通り対応させた、はずである。

- 文字項目（`PIC X`）
- 数字項目（`PIC S9(9)`のような、数字を文字として持つもの）
- 2進数の整数（`COMP`）
- 内部的に10進で持つパック10進（`COMP-3`）
- それぞれの符号付き
- 日付

COBOLのレコード定義でいうと、たとえばこんな感じである。上の条件ファイルの例は、このレコードを相手にしている（これも雰囲気で作った例）。

```cobol
       01  ORDER-REC.
           05  CUST-CODE      PIC X(4).
           05  CUST-NAME      PIC X(16).
           05  ORDER-DATE     PIC 9(8).
           05  ORDER-AMOUNT   PIC S9(9) COMP-3.
           05  ORDER-COUNT    PIC S9(9) COMP.
           05  DISCOUNT       PIC S9(3).
           05  STATUS-CODE    PIC X(2).
```

先頭から数えると、`CUST-CODE`が1桁目から4バイト、`ORDER-DATE`が21桁目から8バイト、`ORDER-AMOUNT`が29桁目から5バイト（パック10進は9桁と符号で5バイトになる）、`STATUS-CODE`が41桁目から2バイトになる。COBOLのプログラムならこの定義を見て項目を扱えるが、SELやSEL95には開始位置と長さと型を自分で指定する必要があった。

このとき思いついた小技がある。Cでは、ポインタをいったん`void *`にして`int *`に変換し、`*`を付けると、そのアドレスにあるバイト列を`int`として読める。レコードを読み込んだバッファの途中を指して同じことをすれば、`COMP`の項目がそのまま整数になる。

```c
int value = *(int *)(void *)(record + start - 1);
```

レコード上のバイナリ表現を、変換処理を書かずにそのまま型として扱える。これはなかなか良いなと思いながら作っていた。

## 括弧付きの式をどう解釈するか

一番苦労したのは、最後の行の式の解釈だった。

ちょうどその頃、背伸びしてコンパイラの本を読んでいた。いわゆるドラゴンブックの邦訳『コンパイラ―原理・技法・ツール』である。書泉ブックタワーで見かけて、かなり思い切って、えいっと買った記憶がある。

なかなか歯ごたえのある本で、読んでいると眠くなる。それでも字句解析と構文解析、構文解析して木の構造にするあたりまでは読んでいた。そこまでの知識がなんとなくあったので、これで作れるんじゃないかと思って書き始めた。

`1 & (2 | 3)`という式は、木にするとこうなる。

```text
      &
     / \
    1   |
       / \
      2   3
```

ドラゴンブック流に文法として書くと、だいたいこんな形になる。

```text
式   → 項 { "|" 項 }
項   → 因子 { "&" 因子 }
因子 → 行番号 | "(" 式 ")"
```

まず文字列を`1`、`&`、`(`のような単位に切り分け（字句解析）、この文法に沿って組み立てる（構文解析）。機械語に落とすのではなく、インタープリタのようにその場で評価する。

ただ、木をデータ構造として作って保存したわけではない。レコードを1件読むたびに、式を頭からパースし直しながら、その場で評価していた。毎回パースしながら木を起こしていく感じである。工夫というより、当時の自分の限界だった。

もっとも、今振り返ると、これは再帰下降で式を評価するときの素直な形でもある。文法の「式」「項」「因子」をそれぞれ処理して呼び合っていくと、呼び出しの入れ子がそのまま上の木の形になる。木をデータとして持っていなくても、評価している間は木をたどっていたことになる。

## 何万人目かの使用者

SEL95は、現場でかなり使ってもらえた。

当時、Webサイトでは来訪者カウンターが流行っていた。ページを開くと「あなたは〇〇人目の訪問者です」と出る、あれである。それをSEL95に取り入れて、起動するたびに「あなたは〇〇人目の使用者です」と出るようにして遊んでいた。

かなり使ってもらえていたので、カウンターは何万とかまで回っていたはずだ。

その後、SEL98というのも作った。そちらはOpenVMSにあったライブラリを使って、今でいうTUIの、少しグラフィカルなターミナルで動くツールにした。

名前の付け方は、相変わらずだった。
