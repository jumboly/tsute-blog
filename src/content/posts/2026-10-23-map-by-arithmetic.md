地図の投影法を調べると、球面を平面に写すための数式がたくさん出てくる。三角関数、対数、楕円体。投影法ごとに何が保たれて何が歪むか。読んでいると、地図を描くにはこれを全部わかっていないといけない気がしてくる。

ただ、私が最初に引っかかったのは、そこではなかった。

初めて地図アプリに触ったとき、地図の描画はライブラリに任せていた。地図はライブラリが描いてくれる。不思議に思ったのは、その上にアイコンを置こうとしたときだった。アイコンが持っている位置情報は緯度経度だけなのに、どういう理屈で画面の何ピクセル目に出てくるのだろう。

球面を平面にする計算があることは、地理の授業で習ったくらいの知識で知っていた。公式は知らなくても、緯度経度を何かのXY座標に変換しているのだろう、というところまでは想像できた。わからなかったのはその先で、XY座標になったとして、それをどうやって画面のピクセルにするのかが思いつかなかった。そのときは自分で作る必要もなかったので、不思議に思いながらもそのままにしていた。

その後、ライブラリの機能だけではやりたいことができなくなって、地図を自分で描くことになった。そこで初めてライブラリの中身を調べたら、メートルとピクセルの対応を、ある基準で決めていた。ああ、そういうことか、と腹落ちした。投影の計算とは別に、どこかで換算の基準を決め打ちしている。

投影の公式は、自分で導けなくても使える。どんな値を入れたらどんな値が出てくるかがわかっていれば、部品として扱える。わかりにくいのは、むしろ出てきた座標を画面に置くところで、そこは数式が勝手に決めてはくれない。

この記事では、簡単な地図の描画プログラムを頭の中で組み立てていく。値を動かして確かめられる教材も作った。

- 教材: [地図は算数で描ける — 教材](https://www.jumboly.jp/map-by-arithmetic/)
- ソース: [jumboly/map-by-arithmetic](https://github.com/jumboly/map-by-arithmetic)

教材は地図ライブラリを使わず、座標からピクセルへの変換を自前で書いて、Canvasに描いている。各章のリンクから、その章の状態で開ける。

## 緯度経度をそのまま描いてみる

最初は投影法のことは忘れる。経度をX、緯度をYとして、そのまま平面に並べてしまう。

経度は-180〜180度、緯度は-90〜90度。横が360、縦が180の長方形になる。これを720×360ピクセルの画面に描くことにする。

```javascript
px = (longitude + 180) * 2;
py = (90 - latitude) * 2;
```

[実装を見る（`plateToPixel()`）](https://github.com/jumboly/map-by-arithmetic/blob/5c6b0d75aca9dc5069438c24e68bc52475dc4c96/src/math.js#L8-L13)

これだけで世界地図が描ける。

一つずつ見ていく。

180を足すのは、画面の左端を0にしたいからだ。経度は-180から始まるので、180を足すと0〜360になる。

90から引くのは、画面のYが下向きに増えるからだ。緯度は北に行くほど大きいが、画面は下に行くほど大きい。90から引くと、北極（90度）が0、南極（-90度）が180になって、北が上に来る。

2を掛けるのは、360度を720ピクセルにすると決めたからだ。1度が2ピクセル。縦も同じ倍率なので、180度が360ピクセルになる。

大阪（東経135.5023度、北緯34.6937度）を入れてみると、`px`は(135.5023 + 180) × 2 = 631.00、`py`は(90 − 34.6937) × 2 = 110.61。720×360の画面の、右寄りの上のほうに点が打たれる。

[教材で試す（緯度経度そのまま）](https://www.jumboly.jp/map-by-arithmetic/?mode=plate)

教材には「90から引くのをやめて、緯度に90を足してみる」というチェックボックスを付けた。付けると世界が上下逆さまになる。式が一つ違うだけで、南が上の地図ができあがる。

これは正距円筒図法（Plate Carrée）のいちばん単純な形である。足し算と引き算と掛け算しか使っていない。

ところで、720×360は誰が決めたのか。

私が決めた。1度を2ピクセルにしたのも私だし、左上を画面の原点にしたのも私である。1度を3ピクセルにすれば1080×540になる。世界地図であることは変わらない。

緯度経度は地球の上の位置を表しているが、画面のどこに何ピクセルで描くかまでは教えてくれない。そこはプログラマーが決め打ちするしかない。この記事は、最後までこの話をしている。

## Webメルカトルで描いてみる

次は、Googleマップや多くのWeb地図で使われているWebメルカトルである。

ここでは、Webメルカトルを「緯度経度を、0〜1の正方形の中の座標に変換するもの」として扱う。メートルもピクセルも、まだ出てこない。

Xは簡単で、経度を0〜1に縮めているだけである。

```javascript
x = (longitude + 180) / 360;
```

第1章で360度を720ピクセルにしていたところを、360度を1にしたと思えばいい。

Yは公式として使う。

```javascript
const phi = (latitude * Math.PI) / 180;
y = (1 - Math.asinh(Math.tan(phi)) / Math.PI) / 2;
```

[実装を見る（`mercatorUnit()`）](https://github.com/jumboly/map-by-arithmetic/blob/5c6b0d75aca9dc5069438c24e68bc52475dc4c96/src/math.js#L27-L35)

この式がどう出てくるかは説明しない。代わりに、入れたら何が出てくるかを見ておく。

- 赤道（緯度0度）を入れると0.5。正方形のちょうど真ん中になる
- 北に行くほど小さくなる。北が上、つまり画面と同じ向きになるように作ってある
- 北緯60度で約0.29、北緯80度で約0.11。赤道から60度までで0.21しか進まないのに、60度から80度までの20度で0.18進む。高緯度ほど引き伸ばされる
- 北緯約85.05113度で0、南緯約85.05113度で1になる。ここで正方形の端に届く

最後の85.05113度は、世界を正方形に収めるために切ったところである。メルカトル図法は極に近づくほど縦に伸びて、極そのものは無限の彼方に行ってしまう。どこかで切るなら、正方形になるところで切ろう、という決め方をしている。

これで、緯度が±85.05113度の範囲に入っていれば、どの緯度経度も0〜1の正方形の中の点になる。あとは正方形を画面に置くだけである。

```javascript
px = x * 256;
py = y * 256;
```

正方形を256×256ピクセルにすると決めた。大阪は`x` = 0.876395、`y` = 0.397135なので、`px` = 224.36、`py` = 101.67。

[教材で試す（Webメルカトル）](https://www.jumboly.jp/map-by-arithmetic/?mode=mercator)

256にも、数学的な理由はない。512でも1000でもいい。教材のスライダーで正方形の大きさを変えると、`x`と`y`はそのままで、`px`と`py`だけが変わる。256は、後で出てくるタイルの大きさとしてよく使われている数字というだけである。

## 平面座標をメートルにしてみる

0〜1の正方形は描くには便利だが、地図の座標としてはちょっと扱いにくい。距離や面積の感覚がつかめない。

そこで、正方形の一辺を地球の赤道の長さにする。WGS84という測地系の赤道半径6,378,137mを使う。

```javascript
const R = 6378137;
const L = 2 * Math.PI * R; // 赤道の円周 = 2πR（約40,075,016.69m）

mx = (x - 0.5) * L;
my = (0.5 - y) * L;
```

[実装を見る（`unitToMeters()`）](https://github.com/jumboly/map-by-arithmetic/blob/5c6b0d75aca9dc5069438c24e68bc52475dc4c96/src/math.js#L50-L55)

0.5を引くのは、正方形の中心（経度0度、赤道）を原点にするため。`my`で引き算の順番が逆なのは、北をプラスにするためである。地図の座標は北が上でプラス、という慣習に合わせている。

これがEPSG:3857と呼ばれる座標系で、Webメルカトルをメートルで表したものだ。大阪は`mx` = 15,084,047.04m、`my` = 4,122,333.71mになる。同じ場所を、0〜1の正方形でも、メートルでも表せる。

ただし、EPSG:3857の1mは、地表の1mと一致するわけではない。メルカトルは高緯度ほど引き伸ばされるので、大阪くらいの緯度では、投影座標の1mは地表の約0.82mにあたる。EPSG:3857は計算のしやすさを優先した座標系で、距離を正しく測るためのものではない[[1]](https://epsg.io/3857)。教材の縮尺バーに「投影座標上」と書いてあるのはそのためである。

さて、メートルの座標が出た。これを画面に描きたい。

……どこに描けばいいのか。

メートルの座標が得られても、ピクセル座標はまだ決まっていない。画面に描くには、少なくとも次のことを決めないといけない。

1. どの座標を、画面のどこに置くか
2. 1mを何ピクセルにするか
3. 東と北を、画面のどちら向きにするか
4. どの範囲を画面に収めるか

どれも、投影法の数式には書いていない。

ここでは、1は「画面の中心に、この座標を置く」、2は試しに「1mを2ピクセル」、3は「東を右、北を上」と決める。4は、画面の大きさと2を決めれば決まる。

画面を640×480ピクセル、中心に置く座標を(cx, cy)とすると、こうなる。

```javascript
px = 640 / 2 + (mx - cx) * 2;
py = 480 / 2 - (my - cy) * 2;
```

[実装を見る（`planeToScreen()`）](https://github.com/jumboly/map-by-arithmetic/blob/5c6b0d75aca9dc5069438c24e68bc52475dc4c96/src/math.js#L84-L89)

`mx - cx`で、中心から東に何m離れているかが出る。それに2を掛けるとピクセルになる。画面の中心は320なので、それを足す。

縦にも横にも、同じ2を掛けている。XとYで別の倍率にすると、地図が縦か横に伸びてしまう。

Yの引き算は、第1章で90から引いたのと同じ理由である。地図の座標は北がプラス、画面は下がプラス。向きが逆なので、足すところを引く。

引き算、掛け算、足し算。第1章と同じことをしている。違うのは、基準を左上ではなく画面の中心にしたことと、倍率を自分で決め直したことだけだ。

1mを2ピクセルにすると、640×480ピクセルの画面には横320m、縦240mしか入らない。街区くらいの範囲である。大阪湾を全部見たければ、1mを0.004ピクセル、つまり1ピクセルを250mにする。

収めたい範囲と画面の縦横比が違えば、どちらかに余白が出るか、はみ出したぶんが切れる。範囲を全部収めたいなら、横に収まる倍率と縦に収まる倍率を出して、小さいほうを使えばいい。

[教材で試す（メートルからピクセルへ）](https://www.jumboly.jp/map-by-arithmetic/?mode=meters)

教材では、計算の欄を「投影後の座標」と「ピクセル座標」に分けて色を変えた。画面をドラッグしたり倍率を変えたりすると、変わった行が光る。投影後の座標は一度も光らない。光るのはピクセル座標だけである。

投影法の数学が決めるのは、メートルの座標まで。そこから先は、プログラマーが決めた基準で決まる。

### 縮尺で決める

1mを何ピクセルにするかは、縮尺で考えることもできる。

縮尺1:10,000なら、現実の100mは地図の上で10mmになる。ここで「地図の上の1mmを4ピクセルにする」と決めれば、10mmは40ピクセル。現実の100mが40ピクセルになる。1mあたりにすると0.4ピクセルである。

```javascript
pxPerMeter = (1000 / 10000) * 4; // 1mは紙の上で0.1mm、それを4倍する
```

[実装を見る（`pxPerMeterFromScale()`）](https://github.com/jumboly/map-by-arithmetic/blob/5c6b0d75aca9dc5069438c24e68bc52475dc4c96/src/math.js#L71-L73)

ここで、1mmを4ピクセルにすると決めたことに注目してほしい。

地図ソフトの縮尺まわりを調べていると、ここで突然DPIという値が出てくる。96とか72とか。私はこれがずっと引っかかっていた。何か物理的に決まった、魔法の数字のように見えるからだ。

でも、やっていることは「1mmを4ピクセルにする」と同じである。1インチは25.4mmなので、1mmを4ピクセルにすると、1インチは101.6ピクセルになる。この「1インチあたりのピクセル数」という言い方がDPIだ。厳密にはDPIはdots per inchで、ピクセルを数えるならPPI（pixels per inch）のほうが正確なのだが、ここではどちらも、画面の論理ピクセルに換算するための基準として扱う。

インチで表す必然性はないし、96という数字にも数学的な必然性はない。CSSでは1インチを96ピクセルと定めている[[2]](https://www.w3.org/TR/css-values-4/#absolute-lengths) ので、Webではこれが基準値としてよく使われる。ただ、これは目の前のディスプレイの実際の画素密度とは別物で、CSSのピクセルは物理的な画素ではない。

1mを何ピクセルにするか。1mmを何ピクセルにするか。1インチを何ピクセルにするか。言い方が違うだけで、どれも換算の基準をどこかで決め打ちしている。

## XYZタイルで描いてみる

Web地図でおなじみの、地図を正方形の画像に分けて読み込む仕組みも、ここまでの算数で説明できる。

0〜1の正方形に戻る。

ズームレベル0では、世界全体を256×256ピクセルにする。ズームレベルが1増えるごとに、縦横を2倍にする。

```javascript
worldSize = 256 * 2 ** zoom;

px = x * worldSize;
py = y * worldSize;
```

ズーム0で256、ズーム1で512、ズーム10で262,144ピクセル。第2章で正方形を256ピクセルにしていたのを、ズームに合わせて大きくしているだけである。

この巨大な世界を、256ピクセルごとに切る。何枚目のタイルに入るかは、256で割って切り捨てればわかる。

```javascript
tileX = Math.floor(px / 256);
tileY = Math.floor(py / 256);

innerX = px - tileX * 256; // タイルの中での位置
innerY = py - tileY * 256;
```

[実装を見る（`tileOf()`）](https://github.com/jumboly/map-by-arithmetic/blob/5c6b0d75aca9dc5069438c24e68bc52475dc4c96/src/math.js#L106-L121)

大阪をズーム10で計算すると、`px` = 229,741.76、`py` = 104,106.45。256で割って切り捨てると、タイルは897番目と406番目になる。タイルの中では左から109.76ピクセル、上から170.45ピクセルのところである。

タイル画像のURLが`…/{z}/{x}/{y}.png`の形になっているのは、この番号をそのまま使っているからだ。大阪なら`…/10/897/406.png`のタイルに写っている[[3]](https://wiki.openstreetmap.org/wiki/Slippy_map_tilenames)。

[教材で試す（XYZタイル）](https://www.jumboly.jp/map-by-arithmetic/?mode=tiles&z=10)

ここでも、ズームレベルは投影の計算に何も関係していない。`x`と`y`はズームを変えても変わらない。ズームレベルというのは、「ズーム0で世界を256ピクセルにし、1増えるたびに2倍にする」という約束に名前を付けたものである。

前の章で1mを何ピクセルにするか決めたのと、考え方は同じだ。換算の基準をズームレベルという段階で決めるか、縮尺やDPIで決めるかの違いである。

## 平面直角座標系で描いてみる

最後に、日本の測量や自治体の地図でよく使われる平面直角座標系を扱う。日本を19の区域に分けて、区域ごとに原点を置いた座標系である。

ここでは大阪湾のあたりを描くので、第VI系を使う。原点は北緯36度、東経136度。京都府、大阪府、福井県、滋賀県、三重県、奈良県、和歌山県がこの系に入る[[4]](https://www.gsi.go.jp/LAW/heimencho.html)。

緯度経度を平面直角座標に変換する式を調べてみる。

……。

PROJを使うことにした。

ブラウザで動かしたいので、教材ではJavaScriptで書かれたproj4jsを使っている。投影法の定義を渡して、緯度経度を入れれば、メートルの座標が返ってくる。

```javascript
const jprcs6 =
  "+proj=tmerc +lat_0=36 +lon_0=136 +k=0.9999 +x_0=0 +y_0=0 +ellps=GRS80 +units=m";
const [east, north] = proj4("EPSG:4326", jprcs6, [135.5023, 34.6937]);
```

[実装を見る（`makeJprcs()`）](https://github.com/jumboly/map-by-arithmetic/blob/5c6b0d75aca9dc5069438c24e68bc52475dc4c96/src/math.js#L131-L143)

大阪は、北向きに-144,802.79m、東向きに-45,598.42mになる。原点が大阪より北東、北に約145km、東に約46kmのところにあるので、どちらもマイナスである。

ここで一つ注意がある。平面直角座標系では、Xが北向き、Yが東向きになっている[[4]](https://www.gsi.go.jp/LAW/heimencho.html)。数学のグラフや画面とは、XとYの名前が入れ替わっている。測量の世界ではこれが普通なのだが、画面に描くときにうっかりXを横に使うと、地図が90度回ったうえに裏返る。

なので、画面の横には測量のY（東）を、縦には測量のX（北）を対応させる。

```javascript
px = 640 / 2 + (Y - cY) * k;
py = 480 / 2 - (X - cX) * k;
```

`k`は1mあたりのピクセル数。第3章の式と見比べると、`mx`が`Y`に、`my`が`X`に変わっただけである。投影の中身はWebメルカトルよりずっと複雑なのに、画面に描くところはまったく同じ算数で済んでいる。

[教材で試す（平面直角座標系）](https://www.jumboly.jp/map-by-arithmetic/?mode=jprcs&overlay=1)

教材では、第1章の描き方（緯度も経度も1度を同じ長さとして並べる）で描いた大阪湾を、点線で重ねられるようにした。点線のほうが東西に広がっている。経度1度の長さは緯度によって違い、大阪あたりでは緯度1度より2割ほど短い。緯度経度をそのまま並べると、そのぶん横に伸びる。

平面直角座標系も万能ではない。中央の経線（第VI系なら東経136度）から東西に離れるほど縮尺の誤差が大きくなるので、使える範囲を区域で区切っている。19もの系に分かれているのは、そのためである。

## QGISやMapLibreの中身が想像できる

ここまでで作ったものを並べると、地図を描く流れはこうなる。

1. 地理データの座標を取り出す
2. 必要なら投影変換する
3. 表示の原点、範囲、倍率を決める
4. ピクセル座標に変換する
5. 点や線を描く

2は数学の仕事で、公式やライブラリに任せられる。3はプログラマーの仕事で、誰かが決め打ちしないと何も描けない。4は、3で決めたものを使った算数である。

QGISもMapLibreも、実際には描画の高速化、ラベルの配置、データの管理、タイルの読み込み、GPUでの描画など、とんでもない量の仕事をしている。でも、どこかで必ず「画面の中心に来る座標」と「倍率」を持っていて、座標をそれで割ったり掛けたりして画面上の位置を出しているはずだ。MapLibreに`center`と`zoom`を渡すのも、QGISの画面の下に縮尺が出ているのも、3を決めているのだと思うと見え方が変わる。

以前、[Android 2.1でオフライン地図を作った話](/posts/android-offline-map-viewer/)を書いた。あのアプリでも、描画処理に渡していたのは地図の中心座標、ズームレベル、画面の幅と高さだけだった。

## 参考資料

1. epsg.io, [“WGS 84 / Pseudo-Mercator - EPSG:3857”](https://epsg.io/3857)  
   **「WGS 84 / 擬似メルカトル - EPSG:3857」**  
   EPSG:3857の定義。楕円体の座標を球として展開していること、適用範囲が南北85.06度までであることが載っている。

2. W3C, [“CSS Values and Units Module Level 4”](https://www.w3.org/TR/css-values-4/#absolute-lengths) - 6.2. Absolute Lengths  
   **「CSS値と単位 モジュール レベル4」**  
   W3C Working Draft, 2024-03-12. 1in = 2.54cm = 96pxと定め、CSSのピクセルは物理的な画素ではなく「参照ピクセル」という見た目の角度で定義されていることが書かれている。

3. OpenStreetMap Wiki, [“Slippy map tilenames”](https://wiki.openstreetmap.org/wiki/Slippy_map_tilenames)  
   **「スリッピーマップのタイル名」**  
   XYZタイルの番号の付け方。ズーム0で1枚のタイルが世界全体を覆うこと、緯度経度からタイル番号を求める式が載っている。

4. 国土地理院, [「平面直角座標系（平成十四年国土交通省告示第九号）」](https://www.gsi.go.jp/LAW/heimencho.html)  
   各系の原点と適用区域、X軸は原点を通る子午線で真北が正、Y軸は真東が正であることが定められている。

5. Natural Earth, [“Natural Earth”](https://www.naturalearthdata.com/)  
   **「Natural Earth（公式サイト）」**  
   教材で使った海岸線データ（1:110m Coastline、1:10m Coastline）の配布元。パブリックドメイン。

6. proj4js, [“proj4js”](https://github.com/proj4js/proj4js)  
   **「proj4js（GitHubのリポジトリ）」**  
   座標系の変換を行うJavaScriptのライブラリ。教材で平面直角座標系の変換に使った。
