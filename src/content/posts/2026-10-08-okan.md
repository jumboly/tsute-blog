おかんというツールを作った。

以前「[SSLインスペクションは「証明書を入れれば終わり」ではない](/posts/ssl-inspection-not-just-certificates/)」に、原因の切り分けで開発者の時間が消えていく、という話を書いた。今回はその続きというか、自分で手を打った話である。

## 目の前のエラーを今どうにかしたい

SSLインスペクションやWebフィルターのある環境では、いろいろなエラーが出てくる。困るのは、何かよく分からないエラーが出ているけど、どっちなのか分からないことである。単に自分の設定ミスなのか、ネットワークのセキュリティ機能のせいなのか。

一応、情報システム部門に問い合わせれば、向こうのログを調べてくれる。でも単純に時間がかかる。こっちはとりあえず今その場で、目の前のエラーを解決したい。問い合わせて待って、などとやっていられない。

なので、その場で検出して切り分けを早くするツールを作った。

## おかん

ツールの名前は「おかん」という。

関西弁のおかんである。おせっかいを焼いて、なんかいちいち見ている。どこ行くの、誰と行くの、と聞いてくる。でも何かあったときには、ちゃんと面倒を見てくれる。その両方を兼ね備えているので、おかんにした。

## やっていることは中継と記録だけ

おかんは、Fiddlerのようにプロキシサーバーとして振る舞うツールである。Windows前提で作っている。[[4]](https://docs.telerik.com/fiddler/knowledge-base/proxy)

機能を有効にすると、まずインターネットオプションのプロキシの接続先をおかんに向ける。ただ、それだけではすべてのツールがこのプロキシを見るとは限らない。なので、環境変数の`HTTP_PROXY`や`HTTPS_PROXY`、`NO_PROXY`の値も変える。この環境変数の扱いは、ツールによって微妙に違ったりもする。[[5]](https://about.gitlab.com/blog/we-need-to-talk-no-proxy/)

```text
各ツール（ブラウザ、CLI、SDK…）
  ↓  インターネットオプション / HTTP_PROXY など
おかん（中継して、通信元のプログラムと通信先を記録する）
  ↓
SSLインスペクション / Webフィルター
  ↓
接続先
```

そして有効にしている間は、通信を中継しながら、通信元のプログラムと通信先を記録する。ツールとしてはそれだけの機能である。

何か変なエラーが出たら、おかんを起動して、もう一度同じ操作をしてみる。通信元と通信先が分かっているので、それで絞り込める。この辺が怪しい、となったら、おかんが実際にその接続先にアクセスしてみて、SSLインスペクションが行われているのか、Webフィルターに引っかかっているのかを検出する。

判定は単純で、実際にアクセスして証明書を見る、ブロック画面かどうかを見る、である。汎用的に配るツールではなく、社内専用と割り切っている。なので、かなり単純な判定基準で判断できる。

## 中身は見ない

Fiddlerのようなと言ったが、おかん自身はSSLインスペクションをしない。

証明書を差し替えて中身まで見れば、もっとリアルタイムで解析できると思う。でもそうすると、今度はおかん起因で何か考慮漏れがあって、さらによく分からない状況になる。切り分けたくて入れたツールのせいで、原因がもう一つ増える。それを防ぎたかった。

あくまでおかんがやるのは通信の中継だけである。それなら単なるプロキシサーバーとして振る舞うだけなので、HTTPのプロトコルに初めから織り込み済みの動きになる。HTTPSなら`CONNECT`でトンネルを張って、あとはバイト列を右から左へ流すだけである。[[1]](https://www.rfc-editor.org/rfc/rfc9110.html#name-connect) トラブルも少ないであろうと考えた。

おかんが証明書の差し替えまでやってしまうと、HTTPの通信に細工をすることになる。途端に対応が難しくなるし、そもそも何がエラーなのかも分からない状況になる。

おかんは、どこへ誰と行ったかは全部見ている。でも手紙の中身までは開けない。

## 作っている途中で怪しまれた

おかんはClaude Codeで作っていた。Claude Codeは、テスト中にいろいろ調査をする。

それで見事に、社内のセキュリティツールに引っかかった。PCに警告のダイアログが出てきた。

検出ログには、当然詳しい理由は書いていない。なので、Claude Codeに「今検出されたけど、何が怪しいと思う？」と聞いてみた。Claude Codeの見解としては、起動時にプロキシの向き先をlocalhostに向けるのは、ランサムウェアなどの典型的な動きに当たるので、それが引っかかったんじゃないか、とのことだった。本当の理由は分からない。

特に連絡は来ていない。多分ログは取られていると思う。

これに対するClaude Codeへの指示としては、「隠しファイルを作ったり、テンポラリにこっそり作ったりせずに、正々堂々とした挙動で確かめていいですよ」という、ちょっと変な指示の仕方をした。

## 記録が取れていない

開発中、自分で使ってみていた。しばらくすると、機能を有効にしているにもかかわらず、記録が取れていないことがあった。

おかしいなぁと思って調べていくと、PACファイルが絡んでいた。PACファイルは、この接続先はプロキシを通す、この接続先は直接つなぐ、といったことを決めるJavaScriptのファイルである。[[2]](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Proxy_servers_and_tunneling/Proxy_Auto-Configuration_PAC_file)

```js
function FindProxyForURL(url, host) {
  // 社内は直接、それ以外はプロキシ、のような判定を書く
  return "PROXY proxy.example.com:8080";
}
```

これがActive Directoryのグループポリシーで配布されている。おかんは、このPACファイルの設定を自分に差し替えたうえで、元のPACファイルを自分の中で処理して、その動きを再現している。

ところが、有効にしている間にグループポリシーの定期更新が走って、設定が上書きされ、元に戻っていた。グループポリシーは、既定では90分ごと（そこから最大30分ずらす）に裏で更新される。[[3]](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2008-r2-and-2008/cc731840(v=ws.10)) おかんが向け直した設定を、グループポリシーが元に戻していたわけである。

対処としては、レジストリを監視して、変更があったら再度上書きするようにした。この場合、変更を検知してから上書きするまでの、ほんの一瞬の通信は取れない。でも何より全然ましだろう、ということでこの対応にしている。これも社内専用ツールなので、「一瞬取れないことがあります」と一言言っておけばいいだけである。

## 落ちたら自分で直せる人だけ

プロキシをおかんに向けたままおかんが落ちると、そのPCは外に出られなくなる。異常終了したときも、できるだけ検出して元の設定に戻すようにはしている。

それでも、配るときには「このツールは上級者向けなので、理屈を理解している人だけが使ってください」と言ってある。プロキシとは何か、環境変数の`HTTP_PROXY`とは何か、が分かっている人なら、落ちたときでも自分で復旧できるからである。

1. R. Fielding, M. Nottingham, J. Reschke, [“RFC 9110: HTTP Semantics”](https://www.rfc-editor.org/rfc/rfc9110.html#name-connect) - 9.3.6. CONNECT  
   **「RFC 9110: HTTPのセマンティクス」**  
   IETF, 2022-06. `CONNECT`メソッドは中継者を通してトンネルを張り、トンネルはメッセージを変えずに2つの接続の間を中継するだけだと定めている。TLSでファイアウォールのプロキシ越しに通信するときによく使われる。

2. MDN, [“Proxy Auto-Configuration (PAC) file”](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Proxy_servers_and_tunneling/Proxy_Auto-Configuration_PAC_file)  
   **「プロキシ自動設定（PAC）ファイル」**  
   MDN Web Docs. PACファイルは`FindProxyForURL(url, host)`というJavaScriptの関数で、リクエストを直接送るか（`DIRECT`）、プロキシに送るか（`PROXY host:port`）を返す。

3. Microsoft, [“Refresh Group Policy”](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2008-r2-and-2008/cc731840(v=ws.10))  
   **「グループポリシーを更新する」**  
   Microsoft Learn（Windows Server 2008のアーカイブ文書）. グループポリシーは再起動やログオンのときに加えて定期的に更新され、既定では90分ごとに、最大30分のランダムなずれを付けて行われる。

4. Progress Telerik, [“The Fiddler Classic Proxy”](https://docs.telerik.com/fiddler/knowledge-base/proxy)  
   **「Fiddler Classicのプロキシ」**  
   Fiddler公式ドキュメント。Fiddlerは起動するとWinINetのシステムプロキシとして自分を登録し、終了するときに登録を外す。

5. Stan Hu, [“We need to talk: Can we standardize NO_PROXY?”](https://about.gitlab.com/blog/we-need-to-talk-no-proxy/)  
   **「ちょっと話そう：NO_PROXYを標準化できないか？」**  
   GitLab Blog, 2021-01-27. `http_proxy`や`no_proxy`の扱いには標準がなく、大文字・小文字のどちらを見るか、`no_proxy`のドメインをどう照合するかがツールや言語ごとに違うことを調べている。
