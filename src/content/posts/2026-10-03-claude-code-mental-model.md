以前、[「クリアしても大丈夫？」](/posts/is-it-ok-to-clear/)という記事を書いた。そこでは、AIの使い方は「こうしなければならない」というものではなく、その人に合わせて使えばいい、という話を書いた。今回も基本的には同じ話である。

AIにどこまで説明するか。どこから任せるか。どこは一緒に考えるか。これも結局、自分を基準にしてさじ加減を決めればいいと思っている。その判断をするうえで、Claude Codeの中で何が起きているのかを、かなり雑に知っておくと便利である。内部実装に詳しくなりたいからではない。**「これはたぶん任せられる」と判断できる範囲が広がるからだ。**

この記事ではClaude Codeの正確な内部実装を説明するつもりはない。実際には構造化されたデータも画像もあるし、もっといろいろな処理がある。あくまで、使うためのメンタルモデルとしてかなり単純化している。まず、これだけ頭に入れておく。

**Claude Codeとモデルは別物で、その間では、ものすごく乱暴に言えば文字列が行ったり来たりしている。**

## Claude Codeは普通のプログラム

Claude Codeと、その中から呼ばれているOpusやSonnetなどのモデルは別物である。Claude Codeは普通のプログラムだ。ファイルを読んだり、コマンドを実行したり、モデルを呼んだりする。一方、モデルは渡された入力を読んで、次に何を返すかを生成する。

たとえば、

```text
src/main.rsを読んで
```

とClaude Codeに頼んだとする。かなり単純化すると、Claude Codeはモデルにこんなものを渡す。

```text
prompt = """
あなたはコーディングを支援しています。

利用できるツール:
- Read
- Edit
- Bash

ユーザー:
src/main.rsを読んで
"""
```

モデルは、それを読んでこんなものを返す。

```json
{
  "tool": "Read",
  "path": "src/main.rs"
}
```

ここでモデルが`src/main.rs`を読んだわけではない。「Readをこの引数で使いたい」と返しただけである。それを受け取ったClaude Codeが、普通のプログラムとしてReadを実行する。そして読んだ結果をまたモデルへ渡す。

無理やり擬似コードにするなら、だいたいこんな世界だと思えばいい。

```text
while true {
    response = call_model(prompt)

    if response.tool == "Read" {
        result = read_file(response.path)
        prompt += result
        continue
    }

    if response.tool == "Bash" {
        result = run_command(response.command)
        prompt += result
        continue
    }

    show_to_user(response.text)
    break
}
```

もちろん実際のClaude Codeがこんなコードでできている、という意味ではない。でも使う側としては、これくらいの理解で十分だと思う。モデルが次にやりたいことを返し、Claude Codeがそれを実行し、結果をまたモデルへ渡す。これをぐるぐる回している。

## CLAUDE.mdもSkillも、魔法ではない

この世界観を持っていると、CLAUDE.mdやSkillもそれほど不思議なものではなくなる。たとえばCLAUDE.mdに、

```text
Rustのコードを変更したらcargo fmtを実行すること。
```

と書いてあったとする。それによってClaude Code本体に、

```text
if Rustのコードを変更した {
    cargo_fmt();
}
```

という処理が追加されるわけではない。モデルに渡される情報の中に、

```text
Rustのコードを変更したらcargo fmtを実行すること。
```

という文字列が増える、と考えればいい。

Skillも同じである。何か新しい能力をモデルへインストールしているというより、「この作業をするときはこうしてください」という追加の説明書を必要なときに読ませている。もちろんCLAUDE.mdとSkillでは読み込まれ方も用途も違う。でも、モデル側から見れば、どちらも判断材料として渡された情報である。

ここまで分かると、設定まわりの見え方も変わる。たとえばステータスラインを変更したいとして、設定ファイルの正確な場所や書式を自分が知らなくても、

```text
設定はどこかのファイルにある
↓
Claude Codeはファイルを探せる
↓
読める
↓
書き換えられる
```

くらいまで想像できれば、「これはたぶんできるな」と判断できる。あとは、

```text
ステータスラインをこうしたい。
今の設定を調べて変更して。
```

でいい。

**詳細を知っているから任せられるのではなく、構造が見えているから任せられる。** ここが結構大事だと思っている。

## サブエージェントも、別コンテキストで動く関数くらいに考える

サブエージェントも、名前だけ見るとかなり特殊な仕組みに見えるが、自分はかなり単純に考えている。

```text
result = subagent("認証周りの実装を調べて")
```

くらいのイメージである。メインのエージェントから仕事を表す文字列を渡す。サブエージェントは別のコンテキストでファイルを読んだり検索したりし、最後に調査結果を返す。中で何十ファイル読んでいても、メイン側に返ってくるのは、

```text
認証はJWTを使っています。
トークン発行はauth.rs、検証はmiddleware.rsです。
```

みたいな結果である。これも「別のエージェントループに仕事を渡して、結果を受け取っている」と考えれば、それほど不思議ではない。

ここまでが、Claude Codeについて知っておきたい構造の話である。では、これが実際の使い方にどう関係するのか。

## AIにどこまで説明するかは、自分を基準にする

人間同士で技術の話をするときは、相手がどこまで知っているかを気にする。「Visitorパターンって通じるかな」「オラクルテストって知ってるかな」「UNIXのパイプみたいなもの、と言って分かるかな」。相手の経験が分からないと、どこから説明すればいいのかを考えないといけない。

AI相手では、ここをかなり雑にできる。自分が昔どこかの教科書で読んだ程度でも、名前が出てくるような一般的な技術概念なら、まず共有語彙として使ってしまっていいと思っている。

```text
ここはVisitorっぽくしたい。
```

```text
UNIXのパイプみたいに、前段の結果を次へ流したい。
```

```text
既存版をオラクルにして全件比較したい。
```

このくらいでいい。二分探索を使いたいときに、二分探索とは何かを説明する必要はない。自分が知っている一般的な知識なら、まずモデルも知っている前提で話す。細かいところはモデル側が補ってくれる。人間相手のように、「この言葉、相手に通じるかな」と毎回考えなくていい。この感覚は、AIとの会話をかなり楽にする。

## 「自分なら作れる」と思えるなら、かなり任せる

もう一つ、自分がAIにどこまで任せるかを決めるときに使っている基準がある。**自分なら、時間をかけて調べれば作れると思えるかどうか。**

これは「自分なら10分で書ける」という意味ではない。かなり調査が必要でもいい。触ったことのないライブラリでもいい。APIドキュメントを何時間も読む必要があるかもしれない。それでも、

> まあ、調べて組み合わせれば普通にできるだろう。

と自分が思えているなら、かなりAIに任せてしまう。

たとえばAWSを普段触っていて、初めてCloudflareを使うとする。Cloudflare WorkersやR2の具体的なAPIは知らない。サービス名すら正確に分からないかもしれない。でもAWSの経験から、

> CDNがあって、DNSがあって、エッジでコードを動かす仕組みがあって、ストレージもあるだろう。たぶんこの辺を組み合わせればできる。

くらいに問題の形が見えている。

それなら、

```text
AWSではこういう構成でやっている。
これをCloudflareで同じ目的を実現したい。
今の構成を見て、対応する機能を調べて組んで。
```

くらいでいい。人間側がCloudflareのドキュメントを全部読んで、Workersとは何か、R2とは何かを理解してからAIに説明する必要はない。

この場合、自分が知っているのはCloudflareの詳細ではない。**「こういう部品を組み合わせれば、この種類の問題は解ける」という構造**である。それが見えているなら、詳細の調査はAIに任せればいい。

## 構造が見えないなら、まず壁打ちする

逆に、

> そもそも何を使えばいいのか分からない。  
> この問題をどう分解すればいいのか分からない。  
> そもそもこの方針で実現できるのかも分からない。

という状態なら、いきなり「作って」とは言わない。まず壁打ちする。

```text
この要件ならどういう構成が考えられる？
選択肢とトレードオフを整理して。
```

から始める。

もちろんAIなら一発でいい答えを出せるかもしれない。でも、自分にも問題の形が見えていないということは、本当に難しい問題なのか、単に自分が知らないだけなのかもまだ分からない。だから、まず一緒に問題を整理する。

自分の中では、AIに任せるか壁打ちするかの境界線は、難易度ではない。**自分の頭の中で、問題の構造が雑にでも見えているか。** これで決めている。

## 詳しく説明するのは、自分たちにしか分からないこと

一般的な技術の説明はかなり省略できる。一方で、詳しく話した方がいいものもある。

```text
このAPIは古い顧客との互換性のために消せない。

この処理は遅く見えるけれど、ここでは順序保証を優先している。

この機能は来月廃止予定なので、大きく作り直したくない。

このプロジェクトでは、速度より既存版との完全互換を優先する。
```

こういう話である。これはモデルがいくら賢くても知りようがない。

なので自分は、**一般的な技術の説明は省略する。自分たちの事情は省略しない。** くらいの感覚で使っている。

「プロンプトは詳しく書いた方がいい」と言われることがあるが、何でも詳しく書けばいいわけではないと思う。AIがすでに知っていることを一生懸命説明するより、AIが知りようのない事情を話した方がずっと価値がある。

## 構造を知ると、「任せられる」の範囲が広がる

ここで最初のClaude Codeの話に戻る。なぜClaude Codeの内部を雑に理解しておくといいのか。仕組みに詳しくなりたいからではない。

構造が分かると、

> ああ、これは設定ファイルを探して書き換えればいいだけだな。

とか、

> これはSkillとして追加の指示を読ませればいいな。

とか、

> この調査は別コンテキストでサブエージェントにやらせればいいな。

と想像できるようになる。

すると、それまで「Claude Codeにそんな機能あるのかな」と思っていたことが、「この道具を組み合わせれば普通にできそうだ」に変わる。つまり、**内部構造を知ることで知識が増えるというより、「これは任せていい」と判断できる範囲が広がる。**

自分にとっては、こっちの効果の方が大きい。

## 自分を基準にすればいい

AIをどう使うべきか、という話にはいろいろな作法がある。プロンプトは詳しく書け。最初に計画を作れ。Skillを用意しろ。細かくタスクを分割しろ。もちろん、そうした方がいい場面もある。

でも、自分はあまり固定的に考えないようにしている。自分が問題の構造を理解できていて、

> これは調べれば普通にできる。

と思えるなら、意図だけ伝えてかなり任せる。一般的な技術用語なら、自分が知っている言葉をそのまま使う。自分にもどう作ればいいか見えていないなら、まず壁打ちする。そして、自分たちにしか分からない事情だけはきちんと説明する。

AIへの頼み方に、万人共通の正解はないと思う。**自分の理解度を基準にして、説明する量、任せる量、壁打ちする量を決めればいい。** その人が知っていることも、経験してきたことも違うのだから、その境界線が人によって違うのは当然である。そしてAIは、そこにかなり柔軟に合わせてくれる。

個人的には、それもAIを使う面白さの一つだと思っている。
