2021年ごろの話である。

以前、[我が人生最高傑作かもしれない仕組みの話](/posts/vb6-classic-asp-rpc/)を書いた。2000年代前半に、VB6とClassic ASPで作ったRPCの仕組みの話だ。

それから20年ほどたって、AWS上のマイクロサービス向けに、C#とASP.NET Coreで共通基盤を作った。自分の中では、これが次点の作品である。

最高傑作ではない。でも、20年たって作ったものとしては、なかなかのものだと思っている。今回はその話と、なぜ一番ではなく次点なのか、という話を書く。

## マイクロサービスは、もう決まっていた

複数のサービスが互いに呼び合う、業務システムの案件だった。マイクロサービスで作ることは、私が関わる時点で決まっていた。

正直なところ、マイクロサービスの採用には多少懐疑的だった。ただ、私は要件定義やアーキテクチャ選定の議論よりも、技術的な部分に専念したかった。なので、その前提はそのまま受け入れて、この条件で開発しやすくするにはどうするか、を考えることにした。

言語はC#にした。大人数で開発することが分かっていたので、型で守れるものは型で守りたかった。

## 書かなくていいものを、書かせたくなかった

前作のときは、CSVの組み立てと分解がシステムの3分の1くらいを占めていた。あれを消したのが前作だった。

今回、消したかったのは、サービス間の通信、認証、ログだ。マイクロサービスでは、どのサービスもこれを必要とする。これをサービスごとに書かせたくなかった。かといって、共通基盤を使うために大量の約束事を覚えてもらうのも避けたかった。

各サービスの開発者には、ビジネスロジックに専念してもらいたかった。これに尽きる。

結果として、サービスの起動部分はこれだけになった。

```csharp
// Program.cs
await AppEntryPoint.RunAsync<Startup>(args);
```

```csharp
// Startup.cs
public void ConfigureServices(IServiceCollection services)
{
    services.AddBackend(); // 共通基盤
    // ここから下は、このサービス自身の都合
    services.AddSingleton<IAddressDictionary, AddressDictionary>();
}

public void Configure(IApplicationBuilder app)
{
    app.UseBackend(); // 共通基盤
}
```

（名前は変えてある。以下のコードも同じ）

`AddBackend()`と`UseBackend()`の2行の裏で、ログ、リクエストIDの補完と伝播、トークンからのユーザー情報の取得、セッションと権限のチェック、エラー応答の組み立て、Swagger、他のサービスを呼ぶHTTPクライアントなどが登録される。コントローラーを書く人は、これらを意識しないで業務処理を書き始められる。

リクエストIDは、入ってきたリクエストになければ補い、ログに勝手に付け、次に呼ぶサービスへ伝播し、レスポンスで返す。利用者からエラーの問い合わせがあったら、画面に出たIDでログを絞り込める。どれも小さな仕組みだけれど、開発者が毎回これを書かなくていい、というところに価値があると思っている。

この目的は、かなり実現できたと思う。実際に使った開発者からも非常によい評価をもらったし、私自身もこの基盤は気に入っている。

## このシステムのためだけに作った

最初から決めていたことがもう一つある。この基盤は、他のシステムに使い回すつもりがまったくなかった。このシステムのためのオーダーメイドだ。

前作も、必要な型だけに対応して、任意のクラスの自動シリアライズなんかは作らなかった。今回も同じで、汎用のライブラリとして整備する気はなかった。そのおかげで、このシステム特有の要件にだけ集中できて、シンプルなものになったと思っている。

ただ、この「オーダーメイドだからシンプル」は、後で書く悔いにつながってくる。

## RPCは通らなかったので、クライアントは手書きにした

私は、処理名・引数・戻り値を中心に扱えるRPC的なWeb APIが好きだ。前作の`CommandName`と`Parameters`からずっとそうで、その話は[POSTでええやん](/posts/post-is-fine/)に書いた。

今回もそれを推した。でも利点を十分に伝えきれず、APIはREST風の方針に決まった。

その条件でクライアントの自動生成にこだわると、生成するための厳密な仕様や規約が要る。パスはこう、メソッドはこう、パラメーターはここに、と決めて、全員にそれを守ってもらう。私はそれよりも、サービスごとの自由度を残したかった。

そこで、サービスの機能をC#のインターフェースとして切り出して、呼ぶ側と受ける側で同じものを使うことにした。

```csharp
// 擬似コード

// 契約。呼ぶ側と受ける側で共有する
public interface IMatchingApi
{
    Task<Response<MatchingResult>> Matching(MatchingRequest request);
}

// 受ける側。いつものコントローラーに、インターフェースを足しただけ
[ApiController]
[Route("matching")]
public class MatchingController : ControllerBase, IMatchingApi
{
    [HttpGet]
    public Task<Response<MatchingResult>> Matching([FromQuery] MatchingRequest request)
    {
        // 業務処理
    }
}

// 呼ぶ側。手書きのクライアント
public class MatchingApi(IApiClient client) : IMatchingApi
{
    public Task<Response<MatchingResult>> Matching(MatchingRequest request)
    {
        return client.SendAsync<Response<MatchingResult>>(
            HttpMethod.Get, route: "matching", query: Query.Create(request));
    }
}
```

呼ぶ側は、DIでインターフェースを受け取って、メソッドを呼ぶだけだ。相手のサービスがローカルで動いていてもAWS上で動いていても、このコードは変わらない。

手で書くのは、ほぼ「HTTPメソッド」「パス」「クエリかボディか」の対応だけだ。コントローラーの属性を見ながら、それに合わせて書けば済む。何個か見本を見れば「ああ、はいはい、こういうことね」と書けるくらいを狙った。

前作でも、プロキシを生成する仕組みやコード生成は作らなかった。20年たっても、そこは変わらなかったことになる。

RESTでも、OpenAPIからクライアントを生成する方法はある。私が選んだのは、サービスごとの自由度と、仕組み全体の単純さのほうだ。仕方なく自動化を諦めたというより、積極的に気に入っている判断である。

同じインターフェースを実装しているので、引数や戻り値の型がずれればコンパイルエラーになる。一方で、HTTPメソッドやパスがコントローラーと一致しているかまでは保証されない。そこは手で書いた部分の責任で、実際に叩いて確かめる。

余談だけれど、見本を見れば分かる、というこのやり方は、今のコーディングエージェントにもそのまま合うと感じている。すべての規約を厳密に書き出さなくても、既存の実装をいくつか見せれば、エージェントはパターンを読み取って書いてくれる。当時は人間の開発者を想定して選んだやり方だった。

## 入口は一つにした

前作では、Classic ASPのファイルは基本的に1枚だけだった。クラス名と処理名を受け取って、`CreateObject`と`CallByName`で振り分けていた。

今回の入口は、冒頭の`AppEntryPoint`だ。Lambdaの中で動いているかどうかを環境変数で見て、Lambdaでなければ普通のWebサーバーとして起動する。Lambdaなら、届いたイベントがAPI Gateway、ALB、SQSのどれから来たのかを見分けて、全部同じASP.NET Coreに流す。このあたりの仕組みは[AWS Lambda『完全に理解した』瞬間](/posts/lambda-fully-understood/)に書いた。

実行環境や入口ごとに、別の業務処理を書かせたくなかった。コントローラーは、自分が何経由で呼ばれたのかを知らない。

送る側にも仕掛けがある。手書きのクライアントが使う`ApiClient`は、接続先のURLのスキームを見て送り方を変える。

```csharp
// 擬似コード
if (url.StartsWith("https://") || url.StartsWith("http://"))
{
    return SendHttpAsync<T>(url, method, header, query, body);
}

if (url.StartsWith("sqs://"))
{
    // メソッド・パス・ヘッダー・ボディを、API Gateway のイベントと同じ形の JSON に詰めて SQS に送る
    return SendSqsAsync<T>(url, method, header, query, body);
}
```

本番の設定では、非同期で呼びたい相手の接続先を`sqs://キュー名`にしておく。開発時は、それを`https://localhost:5101/`に上書きする。すると、同じクライアントがHTTPで直接呼ぶようになる。

SQSで非同期に動く処理でも、ローカルではHTTPで叩いて、ブレークポイントで止めて調べられる。これがやりたかった。

ただし、ここは割り切ったところでもある。基盤が引き受けたのは、非同期で呼び出す口までだ。

同じインターフェースなのに、HTTPで呼べば結果が返り、SQSで呼べば返らない。受ける側の業務処理が失敗しても、SQSの再試行には結び付かない。処理が終わったかどうかの確認や、失敗したときの扱いは、サービス間の約束としてアプリ側に任せた。

ここはうまく解けていないと、作った当時から分かっていた。それでも、これでよいとした。

もう一つ余談。後になってAWS Lambda Web Adapterの存在を知った[[1]](https://github.com/aws/aws-lambda-web-adapter)。Lambdaに届いたイベントをHTTPのリクエストに変換して、普通のWebアプリに渡してくれる。まさにここでやりたかったことで、知ったときは「やられた！」という気分になった。

## 手元で叩いて、止めて、調べられること

前作では、クライアントとサーバーを同じVB6のProject Groupに入れて、HTTPを介さずにサーバーのコードをブレークポイントで止められるようにしていた。

今回も、テストのしやすさには強くこだわった。私にとってのテストのしやすさは、実際に確認・デバッグしやすいことだ。

F5で起動すると、ブラウザでSwagger UIが開く。そこからリクエストを送れば、ブレークポイントで止まる。ローカルでもCognitoやDynamoDBは本物を使い、呼び出し先も設定でAWSとローカルを混ぜられるので、Swagger UIから送ったリクエストが、そのままAWS上のサービスまでつながって動く。

AWSのローカルエミュレーターは、原則として使わなかった。本物との微妙な動作差もあるし、代替環境を作って維持する手間もかかる。開発で使う程度のAWS料金は許容できると判断した。料金を抑えるために、かえって人間の手間を増やしたくなかった、というのが本音だ。

ユニットテストの扱いは、前作と逆になった。前作は急いでいたからこそユニットテストを書いた。今回は、基盤としてユニットテストを必須にはしなかった。

前作はロジックが中心だった。シリアライザのように、小さい単位で往復を確かめられるものだった。今回は、DBや他のサービスの呼び出しが入ってくる。なので、ユニットテストを書くかどうかはケースバイケースだと判断した。サービスを通した確認はJMeterで行った。

## エラーメッセージの名前を、日本語にした

ここも特にこだわったところだ。

```csharp
throw Messages.E0003_データが存在しません.ToException();
```

メッセージを使う場所で、そのメッセージが何を言っているのかがその場で読めるようにした。`E0003`だけだと、書く人も読む人も一覧表を引かないと意味が分からない。

文言に差し込む値があるメッセージは、その数と型を型引数で持たせた。

```csharp
public static Message<string, string> D9002_0_から_1_で入力してください { get; }
    = new("D9002", I18N.T(("ja", "{0} から {1} で入力してください"),
                          ("en", "Please enter a value between {0} and {1}")));
```

差し込む値の数を間違えれば、コンパイルエラーになる。業務処理で例外にして投げれば、あとは基盤が、言語を選び、リクエストIDを付けて返す。

## 引き受けすぎたもの

ここまでが、うまくいったと思っている部分だ。ここからは、うまくいかなかった部分の話になる。

基盤には、入力チェックとDBアクセスも入れていた。

入力チェックは、必須や文字数などを検証する属性を共通で用意した。DTOのプロパティに属性を付けるだけで、共通のエラー体系に沿った入力エラーが返る。便利ではあった。

ところが、共通の属性で足りないチェックは各サービスが自分で属性を作り、属性で書けない業務上のチェックは業務処理の中で書く、という状態になった。ある入力のチェックがどこで行われているのかを知るには、共通の属性、サービスの独自の属性、業務処理の中を、それぞれ見ないといけない。

DBアクセスは、PostgreSQL向けにDapperを薄くラップしたものだった。ここまでは本当に薄かった。

しかし、DBの使い方はサービスごとに違った。DynamoDBを使うサービスもあるし、同じPostgreSQLでも、テナントごとにDBを分けるサービスもあれば、共通のDBを使うサービスもある。それに対応するために、テナントごとの接続先の管理を共通側に持ち込んだ。さらに、複数の接続先にまたがる更新を一つのトランザクションのように扱う仕組みまで入った。薄いラッパーとして始めたものの周りに、これだけのものが積み上がった。

ラッパーが厚くなったことを反省している、という話ではない。薄いままにしておけば問題なかった、とも思っていない。

入力チェックもDBアクセスも、各サービスが自分の都合として扱う処理だ。別々に作っていれば、それぞれのサービスが必要な方式だけで済んだはずだ。テナントごとにDBを分けないサービスは、接続先の管理など持たなくてよかった。

共通基盤にしたことで、元の状態よりも全体が複雑になり、変更もしづらくなった。共通側を変えれば、使っている全サービスに影響する。サービスの事情に合わせて共通側を広げれば、使わないサービスにもその複雑さがついてくる。

そもそも基盤が提供する必要はなかった。そこを、設計判断の誤りだと感じている。

さっき、このシステムのためのオーダーメイドだからシンプルになった、と書いた。システムの外に向けては汎用化しなかったのに、システムの中に向けては、サービスごとの違いを共通側で吸収しようとしてしまった。

各チームからは、共通基盤への追加の要望がいろいろあった。「それは各チームで実装すべきです」と説明して断ろうとしたけれど、説得しきれずに取り込んだものもある。共通化を無条件によいことだと捉える人も、少なくないと感じていた。

DBアクセスは、頼まれて、なんか必要かなぁと思って作った。でも、別にいらんかった。頼まれたのもあるけれど、作ってみたかった、というのもある。そこが敗因かな、と思っている。

通信、ログ、認証のように、システム全体で取り決める必要のあるものに、基盤の責任を絞ればよかった。リクエストIDは全サービスが同じヘッダーで引き継がないと意味がないし、トークンは全員が同じ方法で運ばないと次のサービスで使えない。サービスの呼び出し方も、呼ぶ側と受ける側で揃っていないと成り立たない。だからこそ、基盤が引き受ける意味があった。

入力チェックやDBアクセスは違う。似たコードが複数のサービスに現れることはあっても、サービスの間で揃っている必要はない。共通化できることと、共通化すべきことは違う。

## なぜこれを次点だと思っているのか

並べてみると、20年たっても変わっていないことが多い。

書かなくていいものを、書かなくていいようにする。呼び出しは処理と引数と戻り値で考える。プロキシやクライアントを生成する仕組みは作らない。必要なものだけに対応する。入口は一つにして、そこで振り分ける。手元で止めて調べられるようにする。新しい発明はせず、知っている技術を借りて組み合わせる。

前作は、1週間くらいの突貫工事だった。今回は大人数で使われて、今は別のチームが引き継いで、まだ動いている。規模も期間も、比べものにならない。

それでも次点なのは、技術的に劣るからでも、簡単だったからでもない。

前作は、もっとよくできた可能性はあっても、目的に対して必要十分だった。今回は、目的はかなり達成できて、使った人にも喜んでもらえた。けれど、引き受けすぎた部分がある。

だから、一番ではない。でも、最高傑作から20年たって作ったものとしては、我ながらなかなかのものだと思っている。
