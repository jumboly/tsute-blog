2011年の話である。

仕事で、Androidのオフライン地図ビューアーを作った。端末のOSはAndroid 2.1。私にとって初めてのAndroidアプリで、Androidアプリってどうやって作るんだ、というところから調べながら作った。開発環境は、たぶんEclipseだったと思う。

## 山で地図を使いたい

用途は、山間部の設備を保守しに行くときの道案内だった。

行き先は山奥で、普通の道路がないことも多い。山道や獣道のようなところを通っていく。当然、携帯は圏外なのでオンラインの地図は使えない。一方で、GPSは圏外でも測位できる。だったら地図を先に端末へ入れておいて、オフラインで地図と現在位置を出せばいい、ということになった。

最初は端末選びからだった。山の中で持ち歩くので、落としても壊れにくいものがいい。記憶では京セラの頑丈な端末だったと思うが、機種名は思い出せない。

Androidは当時から機種による違いが多かったので、最初から使う端末を決め打ちにした。いろいろな機種で動かすことは考えない。決まった端末で動かしてみて、問題がなければそれで問題ない。

山の中でGPSがどれくらい使えるのかも気になっていたので、プロトタイプを作って実際に山に登った。

普通のハイキングではまず行かないような場所で、ハイキングコースのようなものはなく、道と呼んでいいのか怪しいところを、みんなで登って帰ってきた。

プロトタイプの地図は、画像を1枚表示して、拡大縮小や移動ができるだけのものだった。地図としての精度は大したことがない。手応えがあったのは、山から帰ってきてからだった。GPSで記録した軌跡を、ちゃんとした地図に重ねてみると、かなりきれいに道に沿っていた。

これなら使える、と判断して本格的に作り始めた。たぶん、山なので周りにビルもなく、きれいに測れたのだろう。

## タイルをZIPに詰め込む

地図はPCで用意した。保守する範囲に合わせてタイル地図を切り出し、SDカードに入れて端末に持たせる。範囲ごとに切り出して、それぞれ別の端末に入れる必要があった。

範囲を絞っても、タイル画像の枚数は膨大になる。小さなファイルを大量にSDカードへコピーすると、とにかく時間がかかる。

そこで、タイルを1つのZIPに詰めた。ZIPの中のファイル名をタイルのパスに対応させておき、Android側では全部を展開せず、必要なタイルだけを探して取り出す。圧縮したかったというより、1つのファイルにまとめたかった。

## 一つ一つは単純な仕組み

アプリの中身も、一つ一つは単純なものだった。

地図は`SurfaceView`を使って、UIスレッドとは別のスレッドで描いた。描画処理に渡すのは、地図の中心座標、ズームレベル、画面の幅と高さだけ。描画処理はスクロールを知らない。スクロールやピンチの操作は別の場所で中心座標やズームを計算して、その結果だけを描画処理に渡す。描画処理は、言われた場所を言われた縮尺で描くだけである。

タイルの読み込みも、描画とは別のスレッドでやっていた。描画処理はキャッシュに必要なタイルを頼む。あればそれで描く。なければ別スレッドがZIPから取ってきて、読み込めたら通知を出す。通知はJavaのObservableのような仕組みで、`notifyChanged`みたいな名前のメソッドだった気がするが、正確には覚えていない。通知が来たら地図を描き直す。

当時の端末はメモリが本当に少なかったので、キャッシュは弱い参照で持っていた。たぶん`WeakReference`だったと思う。GCで消えたら、また読めばいい。だからキャッシュの上限を管理するような仕組みは作らなかった。

キャッシュが消えたときのために何かを作ったわけでもない。表示範囲のタイルがキャッシュになければ読んで、キャッシュに入れて表示する、という処理にしていただけなので、消えていようが消えていまいが関係なかった。そういえば、なんかよく消えるなとは思っていた。

## 指に吸い付く地図を作りたかった

一番こだわったのは、地図の操作感だった。地図描画の滑らかさには、めちゃくちゃこだわった。

当時すでにGoogleマップがあって、一般の人でもGoogleマップを触っている。地図アプリを作る以上、あれが基準になる。比べられるのは避けられない。

WebブラウザでGoogleマップを初めて触ったときも衝撃だったが、それ以上に印象に残っているのが、iPadの「マップ」アプリだった。

それまで知っていた地図の拡大縮小は、画面の中央を基準にするものだった。iPadでは、2本の指でつまんだ場所を基準に拡大縮小する。地図が指に吸い付いてくる。直感的というのはこういうことか、とすごく印象に残っていて、それを再現することにこだわった。

ところが、手元の端末のAndroid 2.1には、ピンチ操作を扱ってくれる便利なAPIがなかった。2本の指の座標は取れるので、そこから先のマルチタッチの処理は自分で書いた。

苦労したのは、つまんだ場所を中心に拡大縮小するための計算である。拡大率を求めるだけなら簡単だが、拡大縮小に合わせて地図の中心座標をどう動かすかがわからない。指の位置がこう変わったら、地図はこう動くはず、というのは個々の例ならわかる。でもプログラムに落とし込むには、式として一般化する必要がある。それがなかなかうまくいかなかった。

そういう計算に決まった解き方があるのかどうかも知らなかった。何を調べればいいのかもわからない。なので、自分で考えるしかないと思っていた。

紙の上に、指がここからここへ動いたら、地図はここに来てほしい、という例をいくつも書いた。どういうパターンで計算すれば全部の例に合うのか、紙とにらめっこしながら探していった。

## コマは飛ぶ。でも指にはついてくる

操作感のためにもう一つ工夫したのが、描画のさばき方だった。

指を動かすたびに、描画の要求をキューに入れる。このとき、要求に通し番号を振り、最新の番号を覚えておく。描画スレッドはキューから普通に順番に取り出すが、描く前に自分の番号と最新の番号を比べる。自分より新しい要求が来ていたら、何もせずに終わる。

当時のコードは残っていないので雰囲気だけ書くと、こんな感じである。

```
// 指が動いたとき
req = { 番号: ++最新番号, 中心, ズーム, 画面サイズ }
キュー.追加(req)

// 描画スレッド
while (true) {
    req = キュー.取り出す()
    if (req.番号 < 最新番号) continue  // もっと新しい要求があるので描かない
    描く(req)
}
```

キューから古い要求を消したり、末尾から最新のものを直接取ったりはしていない。順番に取り出して、古ければ捨てるだけである。

描画処理がスクロールを知らず、中心とズームと画面サイズだけで描けるので、途中の要求を飛ばしても困らない。古い要求が溜まって、地図が指からどんどん遅れていく、ということにはならない。

端末の性能が性能なので、フレームレートはそんなに高くなかったと思う。それでも、表示が指から遅れていくのではなく、コマが飛びながら今の指の位置についてくる。フレーム数は少ないけど、ちゃんと指に吸い付いている、というところまでは実現できたはずだ。

ピンチ中のタイルにも同じような割り切りをした。拡大縮小している間は、手元にあるタイルを伸び縮みさせて描く。その裏で新しいズームレベルのタイルを取りに行き、届いたら順に差し替える。指を離すまで待つのではなく、ピンチしている最中にも差し替わっていく。

タイルのズームレベルは整数だが、操作中のズームは連続的に変わる。記憶では、±0.5くらいまでは同じタイルを使い、それを超えたら別のズームレベルのタイルを頼むようにしていた。新しいタイルがまだなければ、それまでの画像で描く。何もなければ白いまま。読み込めたら通知が来て、描き直される。

画像が粗くても白くても、とりあえず指にはついてくる。きれいな画像は後から来る。

## 15年後に振り返って

アプリは完成して、納品した。ただ、実際に現場で使った人の感想を聞く機会はなかった。どう使われたのかはわからない。これは今でも残念に思っている。

後になって知ったのだが、2010年に出たAndroid 2.2で、`ScaleGestureDetector`というクラスがすでに追加されていた。ピンチの拡大縮小を検出してくれるものである。[[1]](https://developer.android.com/reference/android/view/ScaleGestureDetector) [[2]](https://android-developers.googleblog.com/2010/06/making-sense-of-multitouch.html) 手元の端末は2.1だったし、2.2のことはそもそも調べていなかった。地図の中心をどう動かすかまで面倒を見てくれるわけではないにせよ、苦労した部分の一部が標準で入っていたと知ったときは、なんとも言えない気持ちになった。

最近、この話を記事にしようとAIと話していて、`WeakReference`と`SoftReference`の違いを指摘された。`SoftReference`はメモリの状況を見てGCが消すかどうか決めるが、`WeakReference`は、ほかに強い参照がなければ普通のGCであっさり消される。[[3]](https://developer.android.com/reference/java/lang/ref/WeakReference) [[4]](https://developer.android.com/reference/java/lang/ref/SoftReference) なんかよく消えるなと思っていたのは、たぶんそういうことだった。15年越しに謎が一つ解けた。

私は昔から、難しいアルゴリズムを考えるのが得意ではない。ここは自分の戦う場所ではないと思っていて、とにかく無理をせず、自分のできる範囲で最大限の効果を出す方向でやってきた。100点ではなく70点か80点、場合によっては60点でもいい。難しい処理にすると絶対バグるので、一個一個は多少最適じゃなくても、間違いのないように作る。いわゆるピタゴラスイッチ的なものを目指していた。一個一個はシンプル。でも組み合わせると、なんかちゃんと動く。

当時のコードは、細かく見たら相当雑だったと思う。Androidのことは何も知らないところから始めて、弱参照の違いもわかっていなかった。それでも、初めて作ったAndroidアプリにしては、かなりよくできていたと思っている。
