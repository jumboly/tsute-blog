2000年代前半くらいの話である。正確な年はもう覚えていない。ある案件で、既存システムの仕組みを参考にして、別のシステムを作ってほしいという仕事があった。構成は、当時としてはそれほど珍しくないものだった。

クライアントはVB6で作ったActiveX Document。サーバー側はClassic ASP。参考として渡された既存システムも、同じような構成だった。ただ、ソースを解析してみると、ちょっと気になるところがあった。

## システムの3分の1がCSVだった

クライアントとサーバーの通信にはHTTP POSTを使っていた。送っているのはCSVだった。

何か処理をしたければ、その処理用のASPファイルへCSVをPOSTする。ASP側ではCSVをパースして業務処理をし、結果をまたCSVにして返す。クライアント側では、そのCSVを再びパースして必要なオブジェクトへ詰め直す。

つまり処理を一つ作るたびに、

- CSVを作る
- CSVを読む
- またCSVを作る
- またCSVを読む

というコードを書くことになる。しかも、それぞれの処理ごとにである。

参考ソースを眺めていて驚いたのは、このCSVを作ったり分解したりするコードが、ざっくりシステム全体の3分の1くらいを占めていたことだった。正確に計測したわけではないが、かなりの量だったのは覚えている。

さすがに、

> これをそのまま真似して作るのはしんどいな

と思った。

CSVが悪いわけではない。問題は、業務処理を書く人が、毎回CSVという通信形式まで意識しなければならないことだった。

## .NETで見たものをVB6に持ち込めないか

VB6とClassic ASPを使うこと自体は決定事項だった。ここは変えられない。一方で、ちょうどその頃には.NETが出てきていた。自分も別の案件で.NETを触ったことがあって、SOAPによるWebサービスの仕組みも知っていた。

クライアント側から見ると、サーバーにあるメソッドを呼ぶ。引数にオブジェクトを渡すと、通信時にはXMLへシリアライズされる。サーバー側でそれが復元されて処理される。戻り値もまたXMLになって返ってきて、クライアント側でオブジェクトへ戻る。

それを見ていて思った。

> これと同じような考え方を、VB6とClassic ASPに持ち込めないだろうか。

もちろんSOAPそのものを実装したかったわけではない。本物のRPCのようにプロキシオブジェクトを生成して、リモートのメソッドを本当にローカルメソッドのように呼べるところまでやろうとすると、かなり大変そうだった。コード生成のようなものも必要になりそうだった。

そこまではいらない。欲しかったのは考え方だけだった。サーバー側の処理を名前で指定する。引数には普通のデータを渡す。それをどう通信するかはライブラリ側で面倒を見る。それで十分だった。

今振り返ると、かなりRPCっぽいものだったと思う。

## でも、これを作る工数はなかった

問題が一つあった。そもそも、この仕組みを作る工数なんて取っていなかった。依頼されていたのは、参考システムと同じようなCSV通信の仕組みでシステムを作ることだったからである。RPCのようなものを作りたいと言い出したのは、こちらだった。

勝手に本番システムを全部それで作るわけにもいかない。まず動くものを作って、

> こういう仕組みに変えたい

と客先へデモを見せる必要があった。

だから突貫工事になった。記憶では、ほぼ徹夜で一週間くらいで作った。今なら絶対にやりたくない。

## XMLシリアライザから作った

まず作ったのは、値をXMLへ変換するシリアライザだった。ただし、何でもシリアライズできるようにしようとは考えなかった。VB6のあらゆるクラスを自動的にシリアライズする、などと始めたら、それだけで大仕事になる。必要な型だけに限定した。

まずIntegerやStringなどの基本型。次に、.NETのArrayListに相当するものをVB6で自作した。内部に配列を持っていて、容量が足りなくなれば倍々に広げていく、ごく普通の動的配列である。

Dictionaryも扱えるようにした。そして、

- 基本型
- ArrayList
- Dictionary

をXMLへシリアライズできるようにした。

ここまで来ると、かなりいろいろなデータを渡せる。ただ、業務システムなので表形式のデータも欲しくなる。そこで今度は、ADO.NETのDataTableに相当するものを作った。

これも完全にゼロから考えたわけではない。すでにArrayListとDictionaryがある。しかも、その二つはすでにXMLへシリアライズできる。ならば、それを組み合わせればDataTableのようなものも表現できる。列の情報があって、行の集合がある。それを既存のArrayListとDictionaryで構成する。

そうすると、新しい巨大な仕組みを追加しなくても、かなり構造化されたデータまでクライアントとサーバーの間を行き来できるようになった。この辺は作っていてかなり楽しかった記憶がある。

## 呼び出し方はADO.NETから借りた

次に、クライアント側からどう見せるかを考えた。ここも.NETから借りた。ADO.NETでStored Procedureを呼び出すときのCommandオブジェクトである。

プロキシオブジェクトまでは作らない。代わりにCommandを作る。CommandNameへサーバー側の処理名を指定し、Parameterへ引数を入れて、最後にExecuteする。

当時のソースはもう残っていないので、以下は記憶をもとにした概念的なコードだが、だいたいこんな雰囲気だった。

```vb
Set cmd = New RemoteCommand

cmd.CommandName = "CustomerService.GetCustomer"
cmd.Parameters.Add customerId

Set result = cmd.Execute
```

利用する側はこれだけである。CSVを作らない。XMLを書かない。HTTP POSTについても考えない。サーバーのどの処理を、どの引数で呼ぶかだけを書く。

裏側でXMLになっていようが、HTTPで飛んでいようが、業務コードからは関係ない。元の仕組みで大量に存在していた、CSVを作ったり分解したりするコードをほぼ消すことができた。

## Classic ASPは一枚だけになった

サーバー側もかなり単純になった。Classic ASPのファイルは、基本的に一つだけである。そこへすべてのリクエストをPOSTする。ASP側では送られてきたXMLをデシリアライズして、CommandNameとParameterを取り出す。

CommandNameは、例えばこんな形式にしていた。

```text
CustomerService.GetCustomer
```

前半がCOMのクラス名、後半がメソッド名。

まずクラス名からCOMオブジェクトを生成し、確かVB6の`CallByName`を使って、文字列で指定したメソッドを呼び出していた。

概念的にはこんな感じである。

```vb
Set obj = CreateObject(className)

result = CallByName( _
    obj, _
    methodName, _
    VbMethod, _
    parameter _
)
```

実際には複数の引数を処理したり、戻り値を扱ったり、もう少しいろいろやっていたはずだ。ただ、基本はこれだけだった。

結果はまたシリアライズしてクライアントへ返す。つまりClassic ASPは、通信の入口とディスパッチをするだけの薄い層になった。実際の業務ロジックはVB6のCOM側に置く。

## するとデバッグがものすごく楽になった

ここで、予想していた以上の副作用が出た。

元のシステムでは、

```text
VB6 ActiveX Document
        ↓
     HTTP / CSV
        ↓
   Classic ASP
```

という構成だった。

クライアントはVB6、サーバーはASP。当然、両方をまたいでデバッグするのは面倒だった。

ところが今回の仕組みでは、

```text
VB6 Client
    ↓
RPCのような通信層
    ↓
Classic ASP
    ↓
VB6 COM Server
```

となる。

Classic ASPは、ほとんど何もしていない。業務ロジックという意味では、クライアントもサーバーもVB6である。そこで、開発時には両方を同じVB6のProject Groupへ入れた。そして開発用の通信経路では、実際のHTTP通信をせず、そのままサーバー側のVBコードを呼べるようにした。

正確にどう切り替えていたのかは、さすがにもう覚えていない。記憶では、シリアライズしてデシリアライズするところまでは再現して、最後の呼び出しだけをローカルにしていたように思う。

いずれにしても、クライアント側をステップ実行して、

```vb
cmd.Execute
```

まで進む。そこからさらに進むと、そのままサーバー側のVBコードに置いたブレークポイントで止まる。本番ではHTTPを越えて呼ばれる処理なのに、開発時には普通のローカルプログラムのように一気通貫でデバッグできた。これはかなり快適だった。

## 急いでいたからユニットテストを書いた

この通信基盤にはユニットテストも入れた。ちょうど当時、Extreme ProgrammingやTest Firstといった考え方が話題になり始めていた頃だった。[[1]](https://agilealliance.org/agile101/practices-timeline/) VB6用のユニットテストライブラリも存在していて、それを使った。どのライブラリを使ったのかまでは、もう覚えていない。[[2]](https://vbunit.org/)

ただ、このときテストを書いた理由は、立派な開発手法を実践したかったからではない。

時間がなかったからである。

この仕組みは一週間ほどで作って、デモできるところまで持っていかなければならなかった。そんな状況でシリアライザの奥深くにバグを一つ入れてしまうと、上に乗っているすべての処理がおかしくなる。

ArrayListを入れ子にしたら壊れる。Dictionaryを往復させたら値がおかしくなる。DataTableを送ったら列がずれる。そんなことを一つ一つ実際の画面から確認していたら、たぶん一週間では終わらない。

だったら、

> 基本型は往復できる  
> ArrayListは往復できる  
> Dictionaryは往復できる  
> DataTableも往復できる

と、小さい単位で一つずつ確認しながら積み上げた方が速い。

急いでいたから雑に作ったのではない。急いでいたから、むしろ堅実に作った。これは今でも割と覚えている。

## 少しだけ商売っ気もあった

もう一つ、今書くと少しいやらしい話もある。

納品に必要なものは当然納品した。ActiveX Documentのクライアント、サーバー側のCOM、ディスパッチ用のASP。それだけあればシステムは普通に動くし、保守もできる。

ただ、クライアントとサーバーを同じProject Groupに入れて、一気通貫でデバッグするための開発用の仕掛けについては、納品物から外していた。

こちらで追加開発をすると非常に効率がいい。同じことを納品先でやろうとすると、そこまで快適ではない。

なので、

> 次の仕事もこちらに頼んでもらった方が速い

という、多少の商売っ気も入っていた。

その仕掛けを具体的にどう分離していたかは、もうあまり覚えていない。20年以上前のことである。

## なぜこれを最高傑作だと思っているのか

この仕組みが、自分の仕事人生で一番難しかったものかというと、全然そんなことはない。もっと後には、これよりずっと難しい仕事もやっている。ここで使っている技術も、一つ一つを見ればそれほど難しくない。

動的配列を作る。Dictionaryを扱う。XMLへシリアライズする。文字列でメソッドを呼ぶ。COMを使う。Commandオブジェクトを作る。ユニットテストを書く。分かってしまえば、それぞれは普通の技術である。

でも、この仕事では、その時点で自分が知っていたことをかなりうまく組み合わせられたと思っている。

.NETのSOAPを見て、通信からシリアライズという考え方を持ってきた。ADO.NETからCommandとDataTableの考え方を持ってきた。VB6に足りないArrayListは自分で作った。

すでに作ったArrayListとDictionaryを組み合わせてDataTableを作った。COMと`CallByName`を使って、名前によるディスパッチを作った。クライアントとサーバーの両方がVB6になったことを利用して、Project Groupで一気通貫にデバッグできるようにした。

そして、突貫工事だからこそユニットテストを使って、一つずつ確実に積み上げた。

何か一つ、とんでもなく難しいことをやったわけではない。むしろ逆である。知っているものを組み合わせて、必要以上に難しくせず、ちょうど必要なところまで作った。しかも、そもそも予定されていなかったものを、一週間ほどで動くところまで持っていった。

別の場所にある仕組みを持ってきて組み合わせる、という話は以前[「たぶん作れる」が、本当に作れる時代になった](/posts/probably-buildable-now-buildable/)にも書いた。この仕組みは、その具体的な例になっている。

結果として、システムのかなりの量を占めていたCSVの組み立てと分解は、業務コードからほぼ消えた。開発もずいぶん楽になった。

VB6とClassic ASPという制約は何一つ変えていない。

今振り返ると、この「手持ちの知識を全部うまく使えた感じ」が、自分の中ではかなり気持ちいい。

だから、技術的に一番難しかったという意味ではないけれど、ひょっとすると、我が人生最高傑作かもしれない。
