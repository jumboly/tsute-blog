以前[SEL95の記事](/posts/sel95-record-extract-tool/)を書いていて、OpenVMSのことをいろいろ思い出した。新卒で入った現場で使っていたOSで、結構気に入っていた。

今のOSではあまり見かけない機能がいくつもあったので、思い出せる範囲で書いておく。

## ファイルにバージョンがある

OpenVMSのファイルには、バージョンという概念があった。

ファイルを作るとバージョン1になる。エディタで編集して保存すると、元のファイルはそのまま残り、番号が1つ大きいファイルができる。`PROG.COB;1`、`PROG.COB;2`、`PROG.COB;3`という具合である。[[1]](https://docs.vmssoftware.com/docs/vsi-openvms-user-s-manual.pdf) 過去のバージョンが、ちゃんとファイルシステム上に普通に残っている。

放っておくとどんどん増えるので、`PURGE`というコマンドで最新版だけにする。[[2]](https://docs.vmssoftware.com/docs/vsi-openvms-dcl-dictionary-n-z.pdf) 編集しては残り、たまったら`PURGE`で片付ける。この運用がなかなかよかった。

今で言えば、ファイルシステムに小さなバージョン管理が入っているようなものである。

## PURGEとピザポイント

ただ、`PURGE`にはよくあるトラブルがあった。

当時はタイムシェアリングで、1台のすごく強いOpenVMSのサーバーに、みんながVT端末でつないで編集していた。ソースコードは同じフォルダに全部入っていて、それぞれが担当のプログラムを編集する。

そこで、`PURGE`するときにファイル名を指定せずにやってしまう。ファイル名を省略すると、カレントディレクトリのファイルが全部対象になる。[[2]](https://docs.vmssoftware.com/docs/vsi-openvms-dcl-dictionary-n-z.pdf) 自分のファイルだけでなく、隣の人が編集していたファイルの過去のバージョンまで、きれいに消える。

これはもう、ほぼみんなやらかす。まあ、あるある。自分ももちろんやらかした。詳しくは覚えていない。

みんな、そんなに怒っていなかった。マスターのソースコードは別に管理されていて、そこから各自がファイルを取り出し、そのワークファイルで編集するというルールだったからだ。消えても、そんなに重大な事故にはならない。マスターの管理の仕組みは、新人だったのでよく分かっていなかった。GitやCVSのようなよく知られたものではなく、OpenVMSに組み込みの何かだったのかもしれない。

実害がないうえに、どうせ自分もやらかす。だから、やらかしたときにはお約束があった。消された側が、

「せっかくやる気出てたのに」
「この1個前のやつ、どうしても要ったのになぁ」

と、わざと嘘くさく大げさに嘆くのである。

そして、やらかすと「ピザポイント」が溜まっていく。一定数貯まると、ピザを注文してみんなに振る舞う、というルールだった。

ただし半分ネタで、実際に誰かがおごることはなかった。「これはピザポイントですね」と言って楽しんでいただけである。

## ファイル編成をOSが持っている

OSのレベルで、シーケンシャルファイル、相対編成ファイル、索引編成ファイルがサポートされていた。RMS（Record Management Services）という仕組みで、この3つの編成からファイルの作りを選べる。[[3]](https://docs.vmssoftware.com/docs/guide-to-openvms-file-applications.pdf)

今のOSのファイルは、基本的にただのバイト列である。キーで引ける索引編成ファイルが欲しければ、データベースなりライブラリなりを持ってくることになる。それがOSに最初から入っていた。

現場のデータは、固定長のシーケンシャルファイルか索引編成ファイルに入っていた。COBOLからはそのまま読み書きできる。ただ、RMSのファイルをSQLで引けるわけではない。ちょっと条件を書いてデータを探すことができないので、SELのようなツールが必要になった、というのがSEL95の記事の話である。

## 論理名

論理名という仕組みもあった。自分は、環境変数のようなものだと理解して使っていた。

ディスクやディレクトリに、別の名前を付けられる。`DEFINE`で名前を定義しておけば、ファイルを指定するときに物理的な場所の代わりにその名前を使える。値を複数並べておくと、その順に探してくれるサーチリストにもなる。[[1]](https://docs.vmssoftware.com/docs/vsi-openvms-user-s-manual.pdf)

現場では、当時としては汎用機のような使い方で、ディスクを大量につけて管理していた。そうすると、物理名がすごくバラバラにいっぱいになってしまう。それを論理名で集約して、きちんと管理していた。

## DCL

DCL（DIGITAL Command Language）も珍しかった気がする。基本は、いわゆるシェルスクリプトのようなものである。

`F$`で始まるレキシカル関数というのがあって、文字列の長さを取ったり、ファイルを探したりできた。[[4]](https://docs.vmssoftware.com/docs/vsi-openvms-dcl-dictionary-a-m.pdf) 機能が豊富で、かなりのことができた。

一方で、言語としてはかなり素朴だった。値は整数と文字列しかない。制御構文は、ほぼ`IF`と`GOTO`である。[[1]](https://docs.vmssoftware.com/docs/vsi-openvms-user-s-manual.pdf) 配列もない。

それでも、シンボル名に変数を付け足すことで、擬似的な配列が作れた。DCLでは、シンボルを`'`で囲むとその値に置き換わる。[[1]](https://docs.vmssoftware.com/docs/vsi-openvms-user-s-manual.pdf) なので`ITEM'I'`と書くと、`I`が1なら`ITEM1`になる。あとは`IF`と`GOTO`で繰り返せばよい。

記憶をもとにした雰囲気だが、`ITEM1`から`ITEM3`を順に出すならこんな感じになる。

```text
$ ITEM1 = "APPLE"
$ ITEM2 = "BANANA"
$ ITEM3 = "ORANGE"
$ I = 1
$ LOOP:
$   WRITE SYS$OUTPUT ITEM'I'
$   I = I + 1
$   IF I .LE. 3 THEN GOTO LOOP
```

シェルスクリプトでも、`eval`を使えば同じことはできる。ただ、エスケープが面倒で読みにくく、危ない。bashには本物の配列があるが、添字の配列が入ったのはbash 2.0、連想配列はbash 4.0からである。[[5]](https://git.savannah.gnu.org/cgit/bash.git/plain/NEWS) DCLでは、名前を組み立てるのを素直に書けた。

システムがかなり大きかったので、DCLは主力のツールとしてかなり使われていた。ほとんどの人がCOBOLしか知らず、COBOLでツールを作るのもしんどい。だからDCLが多用されていた。元のSELがDCLで書かれていたのも、たぶんそういうことだと思う。

## COBOLからCを呼ぶ

一番気に入っていたのは、複数のプログラミング言語が簡単に連携できたことだった。

現場はほぼCOBOLがメインで、Cを補助的に使っていた。COBOLからCを呼び出すのだが、実際に連携させたとき、拍子抜けするくらい簡単だった。

これも記憶をもとにした雰囲気だが、COBOL側はこんな感じで呼ぶ。

```cobol
       CALL "CHECK_REC" USING BY REFERENCE ORDER-REC
                              BY DESCRIPTOR COND-TEXT
                        GIVING RESULT-CODE.
```

C側は、それをそのまま受け取る。

```c
int check_rec(char *record, struct dsc$descriptor_s *cond);
```

OpenVMSには、言語をまたいだ共通の呼び出し規約（OpenVMS Calling Standard）があった。COBOL、C、Fortran、Pascalなど、違う言語で書いたプログラム同士が呼び合えることが前提になっている。[[6]](https://docs.vmssoftware.com/docs/vsi-openvms-calling-standard.pdf)

`BY DESCRIPTOR`のところが、OpenVMSらしいところだと思う。文字列の持ち方は言語ごとに違うが、ディスクリプタという共通の形にして渡せば、受け取る側は長さとアドレスをそこから取り出せる。[[7]](https://docs.vmssoftware.com/docs/vsi-cobol-for-openvms-reference-guide.pdf)

ちなみに、OpenVMSを開発した人がMicrosoftに行ってWindows NTを作った、という話も聞いていた。Dave CutlerがDECでVMSの開発を率い、1988年にMicrosoftに移ってWindows NTの開発を率いた、という話である。[[8]](https://news.microsoft.com/features/the-engineers-engineer-computer-industry-luminaries-salute-dave-cutlers-five-decade-long-quest-for-quality/)

## 当たり前ではなかった

主に使っていたのはこのOpenVMSの環境だったので、言語間の連携で苦労した覚えがあまりなかった。というより、言語間の連携はOpenVMSでしかしたことがなかった。

最近、久しぶりにWindowsでCをやって、Rustなどと連携させようとした。ABIを揃えないといけないなど、いろいろ苦労した。OpenVMSでは複数言語の連携が簡単にできていたので、余計に衝撃を受けた。あの頃当たり前だと思っていたものは、当たり前ではなかったらしい。

ちなみにOpenVMSは、今もVMS Software, Inc.（VSI）が開発を続けている。2022年には、x86向けの最初の正式版も出ている。[[9]](https://vmssoftware.com/about/news/2022-07-08-state-of-the-92-release-ready/)
